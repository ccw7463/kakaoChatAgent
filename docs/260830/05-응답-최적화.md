# 05. 응답 최적화

커밋 `eb03ef4`, `41dfefc`, `934e744`, `855dfb9`.

## 프로파일링

먼저 어디서 시간이 새는지 측정했다. `llm.invoke`를 감싸 호출 구간을 기록했다.

```
총 10.06초 / LLM 호출 6회 / 스레드 4개
  0.06~1.67  라우팅 x3 (병렬)      1.6초
  1.68~2.85  메모리 저장           1.2초
  2.88~4.13  검색어 생성           1.25초
  4.13~5.39  Tavily 검색           1.26초
  5.39~10.05 최종 답변             4.67초   (프롬프트 17,521자)
```

### 빗나간 가설

"라우팅 3개가 그래프상 병렬로 그려져 있지만 동기 노드라 실제로는 순차일 것"이라고
의심했으나 **틀렸다.** 측정해보니 langgraph가 스레드풀로 실제 병렬 실행하고 있었다
(스레드 4개, 구간 겹침). 그쪽은 손댈 게 없었다.

## 카카오 말풍선 길이 제한 (실제 버그)

`simpleText`는 **말풍선당 1,000자, 응답당 output 3개**까지인데, 실측 답변이
**1,702자**까지 나왔다. 뒤에 붙는 `📌 참고내용` 링크가 잘려나가고 있었다.

문단 → 문장 → 공백 순으로 경계를 찾아 최대 3개 말풍선으로 나눈다. 8개 경계 케이스 검증.

### 참고내용이 흩어지던 문제

글자 수만 보고 자르니 출처 목록 한가운데가 갈렸다. **본문 800자 근처**에서 재현된다.

```
전:  [본문 800 + 참고1,2]  [참고3]      ← 목록이 갈림
후:  [본문 800]            [참고1,2,3]  ← 답변 / 출처로 분리
```

본문과 참고내용을 먼저 분리하고, 참고내용은 **블록 단위로만** 나눠 제목과 링크가
찢어지지 않게 했다. 출처 몫의 말풍선을 먼저 확보해, 본문이 2,600자로 넘쳐도
출처 3건은 온전히 보존되고 본문에 잘림 안내가 붙는다.

재현 구간(본문 600~1,000자, 20자 간격) 전체에서 흩어짐·찢어짐 **0건** 확인.

### 항상 분리로 통일

수정 후에도 길이에 따라 붙기도(≤1,000자) 떨어지기도(>1,000자) 했다. 사용자 입장에서
볼 때마다 레이아웃이 달라진다. **출처가 있으면 길이와 무관하게 항상 별도 말풍선**으로
통일했다. 길이별 8구간(50~2,600자) 전부 일관 확인.

## 메모리 저장을 응답 경로에서 분리

개인정보·선호도 갱신은 **다음 턴부터** 쓰이는데 답변 전에 실행되어, 매 턴
1~2회(1.2~4.7초)의 LLM 왕복만큼 답변이 늦어졌다.

그래프에서 빼고 **콜백 전송 후** `update_memory()`로 처리한다. 현재 메시지는 이미
대화 이력에 있으므로 답변 품질에는 영향이 없다.

## 검색어 생성 통합

검색 필요 여부(YES/NO)와 검색어 생성이 각각 LLM을 호출하고 있었다. 하나의 프롬프트로
합쳐 왕복 1회를 없앴다. 검색어는 인스턴스 속성 대신 그래프 State로 옮겨 턴 간 참조도
명시적으로 만들었다. 7개 파싱 케이스 검증.

## 검색 컨텍스트 축소

1,000자짜리 답변을 만드는 데 **16,229자**를 프롬프트에 넣고 있었다.

| 설정 | 검색 시간 | 컨텍스트 |
|---|---|---|
| advanced / 5건 / 4,000자 | 1.27초 | 16,229자 |
| **advanced / 3건 / 1,500자** | 1.03초 | **4,500자** |

검색 자체 시간은 파라미터와 무관하게 1초 내외였다. 실제 지렛대는 컨텍스트 크기였고,
이는 최종 답변 생성 속도에 직결된다.

## 메모리 누수

`user_agents` dict가 상한 없이 누적되어, 사용자가 늘수록 컴파일된 그래프와 체크포인터가
계속 쌓였다. `OrderedDict` 기반 LRU로 `MAX_AGENTS`(기본 500) 상한을 두었다.

정리되어도 개인정보·선호도는 Supabase에서 다시 불러오므로 손실은 대화 맥락뿐이다.
정리 후 재방문 시 DB 복구가 동작하는 것까지 확인했다.
